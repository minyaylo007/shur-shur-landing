## 1. Архитектура и назначение

**Назначение.** Продающий лендинг SMM-агентства: услуги, кейсы, отзывы, Instagram-лента,
формы заявки и аудита, быстрые кнопки мессенджеров. Заявки уходят в Telegram.

**Стек.** Next.js 16 (App Router) · React 19 · TypeScript · Tailwind CSS v4 · GSAP и Lenis
(анимации, плавный скролл) · three.js через `@react-three/fiber` (3D-вишня) · zod
(валидация) · vitest (тесты).

**Маршруты.**

| Маршрут | Тип | Что делает |
|---|---|---|
| `/` | редирект 308 | → `/uk` (`next.config.ts`) |
| `/uk`, `/en`, `/he`, `/ro` | статика (SSG) | лендинг на четырёх языках; `/he` — иврит, справа налево (`dir="rtl"`) |
| `/api/lead` | серверный | принимает заявки, проверяет (zod, антиспам, лимит частоты), отправляет в Telegram |
| `/sitemap.xml`, `/robots.txt`, `/icon.svg` | статика | SEO |

**Структура кода.**

```
src/
  app/            маршруты: [locale]/, api/lead/, sitemap.ts, robots.ts, globals.css
  components/
    sections/     секции лендинга (hero, услуги, кейсы, отзывы…)
    conversion/   кнопка мессенджеров, липкая CTA-панель
    forms/        формы заявки и аудита
    three/        3D-сцена
    motion/ ui/ layout/
  dictionaries/   тексты uk.ts / en.ts / he.ts / ro.ts (uk — источник типа Dictionary)
  lib/            site.ts (контакты и готовность каналов), i18n.ts (список локалей и
                  направление письма), валидация, Telegram, посты
public/           изображения и бренд-материалы
tests/            vitest
```

**Переменные окружения** (`.env.example`):

| Переменная | Где | Зачем |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | только сервер | бот, принимающий заявки |
| `TELEGRAM_CHAT_ID` | только сервер | куда бот шлёт заявки |
| `NEXT_PUBLIC_SITE_URL` | сборка | адрес сайта для метаданных, sitemap и OG |

Значения живут в `.env.local` (в git не идёт) и в настройках проекта Vercel. Как две
телеграм-переменные попадают в бой и почему после этого нужен перевыкат — см.
[§7, «Боевые переменные»](#боевые-переменные--githubworkflowssync-vercel-envyml).

## 2. Репозиторий

- **https://github.com/minyaylo007/shur-shur-landing** — публичный, основная ветка `main`.
- В git **никогда** не попадают: `.env*` (кроме `.env.example`), токены и ключи,
  контакты и данные клиентов сверх уже показанного на сайте, внутренние заметки.
- Игнорируются: `/.claude/` (локальное состояние агентов), `/docs/private/` (приватные
  материалы и исследования), `.vercel`, `.next`, `node_modules`.

  публичную историю не вошли.

## 3. Локальный запуск

```bash
git clone https://github.com/minyaylo007/shur-shur-landing.git
cd shur-shur-landing
npm ci
cp .env.example .env.local        # заполнить значения
npm run dev                       # http://localhost:3000 → /uk
```

| Команда | Что делает |
|---|---|
| `npm run dev` | dev-сервер |
| `npm run lint` | ESLint |
| `npm test` | vitest (127 тестов) |
| `npm run build` | продакшен-сборка |
| `npm start` | запуск собранного сайта |

Нужен Node.js 20.9+ (в CI — 22).

> **Windows:** vitest падает, если буква диска в пути строчная (`c:\…`). Запускать из
> пути с заглавной буквой: `cd "C:/Users/…"`.

## 4. Удалённый запуск (сервер разработки)

Проект развёрнут на общем Linux-сервере разработки под отдельным пользователем.
На машине работают и другие проекты — их каталоги и сервисы не трогаем.

| Что | Где |
|---|---|
| Рабочая копия | `~/repos/shur-shur-landing` |
| Dev-сервер | юнит `ihor-shur-dev`: `next dev` на `127.0.0.1:8011` (наружу не открыт) |
| Секреты | `~/repos/shur-shur-landing/.env.local`, права 600 |
| Реестр портов | `~/maestro/PORTS.md` — новый порт сначала вписать туда |

Посмотреть сайт со своего компьютера — через SSH-туннель:

```bash
ssh -N ace-shur                   # алиас в ~/.ssh/config, LocalForward 8011
# затем открыть http://localhost:8011
```

Управление dev-сервером: `systemctl --user status|restart ihor-shur-dev`,
логи — `journalctl --user -u ihor-shur-dev -n 50`.

## 5. Дирижёр и рабочие сессии

### Роли

**Дирижёр** «🍒 SHUR-SHUR — дирижёр» — постоянная сессия Claude Code с Remote Control,
видна в приложении отдельным чатом. **Код не пишет и разработку не ведёт.** Его работа:

- знать состояние проекта, архитектуру, документацию и текущие задачи;
- ставить задачи рабочим сессиям с чётким контекстом и ограничениями;
- следить, чтобы каждая сессия закончила изменения через `commit + push`;
- принимать результат: сверять коммиты, CI и итог, возвращать недоделанное;
- обновлять документацию и статус проекта.

**Рабочая сессия** — разработка, тесты, деплой, исправления. Одна сессия — одна задача.

**Модели.** Дирижёр и рабочие сессии работают на Opus. Fable используется только для
глубокого анализа — отдельной сессией с узким заданием:
`session.sh newf shur <файл> claude-fable-5-1`. Рутина, приёмка и статусы на Fable не идут.

### Запуск дирижёра

Дирижёр работает под systemd (`ihor-conductor@shur`): поднимается после сбоя и
перезагрузки сервера и продолжает ту же беседу.

```bash
conductor.sh lead shur ~/repos/shur-shur-landing "🍒 SHUR-SHUR — дирижёр"   # первый запуск
conductor.sh ls                   # состояние всех дирижёров
conductor.sh restart shur         # перезапуск (без нужды не делать, см. раздел 9)
lead-say.sh shur "<одна строка>"  # написать дирижёру из терминала
```

Бриф проекта для дирижёра — `~/maestro/leads/shur.md`, общие правила дирижёров —
`~/maestro/leads/_rules.md`, правила владельца — `~/maestro/OWNER-RULES.md`,
статус проекта — `~/maestro/status/shur.md`.

### Новая рабочая сессия

1. Дирижёр пишет задание в `~/maestro/tasks/shur-<тема>.md`. **Первая строка — имя
   сессии** по-русски: `🍒 SHUR-SHUR · форма аудита: валидация ника`.
2. Поднимает сессию:

```bash
session.sh clone shur ~/maestro/tasks/shur-<тема>.md   # свежий git clone и своя ветка —
                                                        # для всего, что меняет код
session.sh newf  shur ~/maestro/tasks/shur-<тема>.md   # в общей копии — для анализа
session.sh ls | logs <id> | rm <id>
```

`clone` делает `git clone` в `~/work/shur-<время>/shur-shur-landing`, копирует
`.env.local` и запускает сессию уже внутри клона — она сразу начинает работу.

### Шаблон задания

```markdown
🍒 SHUR-SHUR · <что сделать, 3–6 слов>

Зачем: <какую проблему решаем>
Готово, когда: <проверяемые критерии>
Как проверить: npm run lint && npm test && npm run build; <ручная проверка>
Ограничения: репозиторий публичный — без секретов и данных клиентов; не трогать <…>
В конце: ветка → commit → push → PR; сообщить дирижёру итог и ссылку на PR.
```

### Приёмка дирижёром

- ветка запушена, коммиты осмысленные, незакоммиченного не осталось;
- CI по PR зелёный;
- критерии задания выполнены — проверено, а не со слов сессии;
- документация обновлена, если менялось поведение;
- принятая сессия удалена (`session.sh rm <id>`), статус проекта обновлён.

## 6. Обязательный Git workflow

Для **каждой** сессии, меняющей код:

```
git clone (или session.sh clone)
  → git switch -c feat/<тема> | fix/<тема>
  → изменения
  → npm run lint && npm test && npm run build
  → git add <явный список файлов>            # не git add -A
  → git commit -m "<что и зачем>"
  → git push -u origin <ветка>
  → Pull Request в main → CI зелёный
  → merge в main  =  выкат в прод (раздел 7)
```

Правила:

- `main` — всегда рабочая версия; `push --force` в `main` запрещён.
- Сообщение коммита отвечает на «что изменилось и зачем», а не «fix».
- Незакоммиченная или незапушенная работа считается несделанной.
- Слияние в `main` — только после зелёного CI и согласия владельца.

## 7. CI/CD и порядок деплоя

### CI — `.github/workflows/ci.yml`

На каждый push в любую ветку и на каждый pull request: `npm ci` → `lint` → `test` →
`build`. Параллельные прогоны одной ветки отменяют предыдущие.

### Деплой — `.github/workflows/deploy.yml`

- **Автоматически:** после **успешного** CI на push в `main`. Выкатывается ровно тот
  коммит, который проверил CI. На pull request и форках деплой не запускается.
- **Вручную:** GitHub → Actions → Deploy → Run workflow, поле `ref` — коммит, тег или
  ветка. Этим же способом делается откат.
- Шаги: `vercel pull` → `vercel build --prod` (в страницы вшивается отпечаток сборки —
  meta `x-build-sha` с SHA коммита, см. `src/lib/build.ts`) → проверка, что отпечаток
  попал во все четыре предсобранные локали → `vercel deploy --prebuilt --prod` →
  смока боевого домена `scripts/smoke-production.sh`.
- **Смока выката** (`scripts/smoke-production.sh <адрес> <SHA>`) требует от боевого
  домена: четыре локали ровно по 200, в теле каждой наш `canonical`, на каждой
  отпечаток ИМЕННО выкаченного коммита, апекс — 308 на `/uk` без петли.
  Ответ «страница наша, но сборка предыдущая» — переходное состояние края Vercel
  (кеш PoP сбрасывается не одномоментно): такой адрес перепрашивается раз в 15 с,
  суммарно не дольше 4 минут, и только потом краснеет. Ответ «не 200» или «не наша
  страница» ожиданием не лечится и валит выкат сразу. Обе ручки — `SETTLE_BUDGET_SECONDS`
  и `SETTLE_DELAY_SECONDS`; сама смока проверяется на подделке края:
  `FAKE_SCENARIO=converge|stuck|foreign|old-build node scripts/fake-edge.mjs`.
- Работает в окружении GitHub `production` — в Settings → Environments туда можно
  добавить обязательное подтверждение перед выкатом.
- Нужны секрет `VERCEL_TOKEN` и переменные `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`
  (переменные уже заданы). Пока нет токена, деплой **пропускается с
  предупреждением**, а не падает.

> Если у проекта Vercel включена своя интеграция с GitHub, выберите **одно**:
> либо она, либо этот workflow, иначе каждый коммит будет выкатываться дважды.

### Боевые переменные — `.github/workflows/sync-vercel-env.yml`

Сборке нужен только `NEXT_PUBLIC_SITE_URL`; **заявкам** нужны ещё две переменные
времени работы, и без них `/api/lead` честно отвечает `502 delivery_failed`, а в лог
пишет «Telegram bot NOT CONFIGURED»:

| Переменная | Где лежит значение | Что без неё |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | секрет GitHub того же имени | заявки не уходят в Telegram |
| `TELEGRAM_CHAT_ID` | секрет GitHub того же имени | заявки не уходят в Telegram |

Значения **живут только в секретах GitHub** и в окружении production Vercel. В git их
нет, в логах Actions они маскируются, в отчёты и PR не попадают. Смотреть их через
`vercel env ls` бесполезно: для секретов колонка value всегда `Encrypted`.

**Как перенести:** Actions → **Sync Vercel env** → Run workflow. Запуск только ручной,
триггеров на push нет. Для каждого из двух имён сценарий снимает прежнее значение,
если оно есть, и заводит текущее в окружение production; значение передаётся
стандартным вводом, а не аргументом команды (аргумент виден в `ps`). Прогонять можно
сколько угодно раз подряд — результат тот же. Если секрет в репозитории пуст или его
нет, сценарий падает **до** первой записи: пустое значение в бою хуже отсутствующего.

**После синхронизации обязателен перевыкат.** Переменные времени работы вшиваются в
выкат, а не читаются из настроек проекта на лету: пока не прогнали Deploy, на сайте
живёт окружение прежнего выката и форма по-прежнему отвечает 502. Порядок такой:
Sync Vercel env → Deploy (`ref=main`) → отправить в форму настоящую заявку и убедиться,
что пришёл `200 {"ok":true}` и сообщение упало в группу.

> Проверяя заявкой, помните о двух ловушках маршрута: поле-приманка `extra_field`
> должно быть пустым, а `elapsedMs` — не меньше 3000 мс для `kind: "lead"` и 1200 мс
> для `kind: "audit"`. Нарушите любую — получите `200 {"ok":true}`, при котором
> **ничего не отправлено**: так маршрут отвечает ботам. Если тот же запрос до
> синхронизации давал 502, значит он проходит именно доставкой, а не тихим сбросом.

**Смена токена бота** (завели нового бота, отозвали старый): обновить секрет
`TELEGRAM_BOT_TOKEN` в репозитории → прогнать Sync Vercel env → прогнать Deploy
(`ref=main`). Три шага, кода трогать не нужно.

### Порядок деплоя

1. PR с зелёным CI → merge в `main`.
2. CI на `main` зелёный → Deploy выкатывает на Vercel.
3. В сводке прогона Deploy — адрес выката и коммит; открыть сайт, проверить форму.

## 8. Откат (rollback)

Выберите самый быстрый подходящий способ:

1. **Мгновенно, без сборки — Vercel.** Dashboard → проект → Deployments → предыдущий
   рабочий выкат → **Instant Rollback**. Или CLI: `vercel rollback <url-выката>`.
   Git при этом не меняется — сразу после этого сделайте способ 3, иначе следующий
   merge вернёт поломку.
2. **Выкатить конкретный рабочий коммит.** Actions → Deploy → Run workflow →
   `ref` = SHA последнего рабочего коммита (он есть в сводках прошлых прогонов
   Deploy и в `git log`).
3. **Исправить историю.** `git revert <плохой-коммит>` → PR → CI → merge → автодеплой.
   Не переписывать историю `main` через `reset` и `push --force`.

## 9. Расход токенов и правила экономии

### Что случилось

После сброса лимита Fable большая часть дневного лимита ушла за сутки. Разбор полей
`usage` в транскриптах сессий сервера разработки (с дедупликацией по id сообщения):

| Показатель за сутки 12.09 (UTC) | Значение |
|---|---|
| Запросов к Fable | 428 |
| Сессий, которые их сделали | 6 — постоянные дирижёры проектов |
| Запись в кэш промпта | 41,0 млн токенов |
| Чтение из кэша | 231,8 млн токенов |
| Ответ модели | 0,23 млн токенов (**0,1 %** от объёма) |
| Средний контекст одного запроса | ≈ 637 тыс. токенов |
| Самый большой контекст | ≈ 879 тыс. токенов и рос каждый час |
| Расход ночью | 5–9 млн токенов в час без участия человека |

На локальном компьютере Fable в эти дни не использовался — весь расход пришёлся на
дирижёров на сервере.

### Подтверждённые причины

1. **Дирижёры опрашивали сессии по циклу круглосуточно** — 10–28 пробуждений в час.
   Каждое пробуждение перечитывало всю беседу дирижёра, даже если ничего не случилось.
   Самый дорогой час (29,9 млн) совпал с самым частым опросом (28 пробуждений).
2. **Беседа дирижёра не ограничивалась по размеру** — до ~880 тыс. токенов на запрос.
3. **Холодный кэш после перезапусков и смены модели.** Кэш промпта свой у каждой модели
   и процесса. 13.09 было 76 перезапусков за полдня; 15 запросов к Fable дали 4,5 млн
   токенов записи в кэш — около 300 тыс. на запрос.
4. **Сторож моделей «мигал»:** раз в час возвращал всех шестерых дирижёров на Fable и
   через минуту ошибочно видел старое сообщение о лимите в перерисованной беседе —
   12 перезапусков в час.

### Вероятное, но не доказанное

- Точный вес чтения и записи кэша в лимите тарифа не опубликован — посчитать долю
  лимита по каждой причине нельзя. По объёму доминирует повторное чтение контекста.
- Часть записи в кэш (41 млн при всего двух перезапусках 12.09) могла дать истекающая
  между пробуждениями жизнь кэша (TTL). По логам это не проверяется.

### Что внедрено

| Мера | Где |
|---|---|
| Работа **по событиям**, без циклов опроса: сторож `session-events` раз в 10 минут без вызова модели сообщает дирижёру о завершённой сессии; сводка владельцу — таймерами в 09:00 и 20:00 | `~/bin/session-events.sh`, таймеры `ihor-session-events`, `ihor-status-am/pm` |
| **Потолок контекста**: беседа сжимается на 200 тыс. токенов у дирижёров и у всех новых сессий | `--autocompact 200000` в запусках |
| **Дирижёры и рабочие сессии — на Opus.** Fable — только отдельной сессией для глубокого анализа (архитектура, сложная причина сбоя, план крупной фазы) с узким заданием. Сторож больше не возвращает дирижёров на Fable (решение владельца 13.09) | `~/bin/model-watch.sh`, правила владельца, п. 26 |
| Не больше **8** фоновых сессий на машине (проверяется при запуске) и 3 на проект | `session.sh`, правила дирижёров |
| Перезапуск дирижёра без нужды запрещён; принятые сессии удаляются | правила владельца, п. 16 и 25 |

Ожидаемый эффект: контекст на запрос ≤ 200 тыс. вместо ≈ 640 тыс. в среднем (≈ 3×) и
почти нулевой расход в часы без событий вместо 5–9 млн токенов в час.

### Правила для агентов

- Не включать циклы опроса — ждать события.
- Не выводить большие файлы и логи целиком — `tail`, `grep`, `head -50`.
- Прочитал план или бриф — держать выжимку в статус-файле, не перечитывать на каждом ходу.
- В чат — коротко; длинное — в файлы.
- Не держать в беседе то, что лежит в файлах.
- Одна сессия — одна задача; не дублировать работу другой сессии.

### Как проверить эффект

Через 24–48 часов на сервере: `python3 ~/bin/token-usage.py ~/.claude/projects` — запросы,
запись и чтение кэша по дням, моделям, проектам и часам. Сравнить с таблицей выше.
