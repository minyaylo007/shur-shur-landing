# monobank: регулярные платежи (подписка) — выжимка

Источник: документация эквайринга monobank, раздел «Регулярні платежі»
(monobank.ua/api-docs/acquiring), прочитана 18.11.2026. Код: `src/lib/billing/mono.ts`,
вебхук — `src/app/api/billing/mono/route.ts`.

**Что проверено, а что нет.** Всё ниже — по документации. Ни один запрос к monobank
вживую не делался: токенов (ни тестового, ни боевого) у нас ещё нет. Непроверенное
помечено «⚠ не проверено».

## Доступ

- База: `https://api.monobank.ua`. Каждый запрос — с заголовком `X-Token`.
- Боевой токен выдаётся в кабинете `web.monobank.ua` (нужен подключённый интернет-эквайринг
  на ФОП). Тестовый — на `api.monobank.ua` (личный кабинет API, «тестовий токен»).
- Тестовая среда — тот же адрес с тестовым токеном: деньги не списываются, принимается любая
  карта с верной контрольной цифрой (Luhn), Apple Pay / Google Pay не работают.
- Ошибки: HTTP 400/403/404/405/429/500 с телом `{errCode, errText}`.

## Методы

| метод | что делает |
|---|---|
| `POST /api/merchant/subscription/create` | создаёт подписку, возвращает страницу оплаты |
| `GET /api/merchant/subscription/status?subscriptionId=` | состояние подписки |
| `GET /api/merchant/subscription/payments?subscriptionId=&dateFrom=` | списания по подписке |
| `GET /api/merchant/subscription/list?dateFrom=` | все подписки мерчанта |
| `POST /api/merchant/subscription/edit` | `{subscriptionId, action: "cancel", refundAmount?}` — отмена |
| `POST /api/merchant/subscription/remove` | `{subscriptionId}` — удаление НЕоплаченной подписки |
| `GET /api/merchant/pubkey` | открытый ключ для проверки подписи вебхука |

### create — тело

| поле | значение |
|---|---|
| `amount` | сумма в минимальных единицах (1500 = 15,00) |
| `ccy` | ISO 4217, по умолчанию 980 (UAH). Мы шлём 978 (EUR) |
| `interval` | `"1d"`, `"2w"`, `"1m"`, `"1y"` — у нас `"1m"` |
| `redirectUrl` | куда вернуть человека после оплаты — `/client/<id>?paid=1` |
| `webHookUrls` | `{chargeUrl, statusUrl}` — оба на `/api/billing/mono?c=<id>` |
| `validity` | сколько живёт страница оплаты, секунды; по умолчанию 24 ч, максимум 30 дней |

Ответ: `{subscriptionId: "s2_…", pageUrl}`. Первое списание — когда человек оплатит на
`pageUrl`; дальше monobank списывает сам раз в интервал.

**Валюта.** ⚠ не проверено: схема `ccy` допускает 978, но примет ли эквайринг ФОП подписку
в евро, покажет только запрос с токеном (нужен ещё и валютный счёт или конвертация на
стороне банка). Запасной путь готов: задать `MONO_PRICE_UAH` (целые гривны) — тогда
списывается гривна (`ccy` 980), а на странице стоит «15 € (≈ N грн)». Проверка: создать
тестового клиента, нажать «Оформити підписку»; ответ «не вдалося відкрити сторінку оплати»
и `subscription/create` с 400 в логе — значит, евро не принимается.

### status — ответ

`status`: `active` | `cancelled`. Ещё: `startDate`, `endDate?`, `amount`, `ccy`,
`interval`, `nextChargeDate?`, `cancellationDesc?`, `summary: {totalPaid, totalFailed}`,
`walletData: {cardToken, walletId, status: new | created | failed, failureDescription?}`.

### payments — ответ

`{payments: [{amount, ccy, status: new | success | failed, chargedAt}], pagination}`.
`dateFrom` обязателен; есть `dateTo`, `limit`, `page`.

### Откуда эти поля и что, если они окажутся другими

Поля ответов взяты не с текста страницы, а из схемы OpenAPI, которую страница документации
подгружает скриптом: `https://monobank.ua/assets/openapi-data-CzHxXBxW.js` (имя файла
меняется при пересборке их сайта), схемы `SubscriptionStatusResponse` и
`SubscriptionPaymentsResponse`. На самой странице они видны только во вкладке
«Response samples → 200». Дословно, 18.11.2026:

```
status:{type:"string",enum:["active","cancelled"],example:"active",description:"Статус підписки"}
nextChargeDate:{type:"string",format:"date-time",example:"2024-07-01T14:15:22Z",description:"Дата наступного списання"}
endDate:{type:"string",format:"date-time",example:"2024-06-20T09:30:15Z",description:"Дата коли регулярний платіж скасували"}
payments:{type:"array",items:{type:"object",required:["amount","status","chargedAt","ccy"], …
  status:{type:"string",enum:["new","success","failed"],example:"success",description:"Статус платежу"}
  chargedAt:{type:"string",format:"date-time",example:"2024-06-01T14:15:22Z",description:"Дата коли було списання"}
pagination:{type:"object",required:["totalItems","itemsPerPage","currentPage","totalPages"], …
```

Это схема, а не живой ответ: живого никто из нас не видел. Поэтому разбор
(`parseStatus`, `parsePayments`) устроен с запасом:

- понимает близкие написания: `state`, `canceled`, `list`/`items` вместо `payments`,
  `chargeDate`/`paidAt`/`date`, даты числом (секунды или миллисекунды), любой регистр;
- непонятный ответ НЕ ухудшает состояние: статус, дата оплаты и дата списания остаются
  прежними, в записи ставится `unclearAt`, и клиент, который уже платил, остаётся открыт,
  пока ответ не станет читаемым;
- если список платежей не прочитан, а `summary.totalPaid` > 0 — оплата засчитывается
  (месяц до `nextChargeDate`, иначе от `startDate`);
- в журнал идёт одна строка `[billing] monobank answer not understood…` с ИМЕНАМИ ключей,
  без значений (в ответе есть токен карты). Эта строка — сигнал поправить разбор.

Чего запас не покрывает: клиент платит ВПЕРВЫЕ, а ответ не читается вовсе и счётчика
`summary.totalPaid` в нём нет — кабинет останется закрыт до правки разбора (в журнале
будет та же строка).

### Проход в тестовой среде

```
node ops/billing/test-cycle.mjs --id <id тестового клиента>          # ссылка на оплату
node ops/billing/test-cycle.mjs --id <id тестового клиента> --check  # после оплаты
```

Скрипт подписанно просит сайт (`/api/cabinet/billing-test`), сайт работает своим
`MONO_TEST_TOKEN` — проверяется тот же код, что за кнопкой, вместе с вебхуком. `--check`
печатает имена ключей ответов (значения — только типы), что прочитал разбор, сохранённое
состояние и итог `accessOf`. Принимается только клиент с пометкой «тестовый»; без
тестового токена на сайте скрипт так и говорит.

## Состояние у нас

В записи клиента (`billing`): `none` → `pending` (подписка создана, оплаты не было) →
`active` → `cancelled`. Оплаченный период считаем сами: последнее успешное списание +
календарный месяц.

| что видит клиент | условие |
|---|---|
| результаты открыты, «Підписка активна» | есть успешное списание, месяц не истёк |
| открыты ещё 3 дня, «Списання не пройшло» | месяц истёк, подписка `active`, нового списания нет |
| закрыты | 3 дня прошли; или подписка отменена и оплаченный месяц кончился; или оплат не было |
| открыты, «Оплата скоро» | токена нет — оплата на сайте выключена |

## Неуспешное списание

⚠ Документация не говорит, повторяет ли monobank неуспешное списание и отменяет ли
подписку сам. В `payments` такое списание приходит со `status: failed`, в `status` растёт
`summary.totalFailed`, у карты может стать `walletData.status: failed`. Поэтому мы на
поведение банка не полагаемся: доступ держится на дате последнего УСПЕШНОГО списания
плюс 3 дня запаса. Спишет банк повторно — доступ продлится сам; не спишет — закроется.

## Отмена

- Оплат ещё не было (`pending`) — `remove`.
- Оплаты были — `edit` с `action: "cancel"`: `remove` после первой оплаты monobank
  отклоняет (errCode 1001). Доступ остаётся до конца оплаченного месяца.
- Возврат денег — тот же `edit` с `refundAmount`; на сайте кнопки нет, делается вручную
  (или в кабинете monobank).
- Удалить клиента с действующей подпиской кабинет не даёт: запись исчезла бы, а списания
  продолжились.

## Вебхук

- monobank шлёт POST на `chargeUrl` / `statusUrl`; заголовок `X-Sign` — base64 подписи
  ECDSA (DER) над SHA-256 сырого тела. Открытый ключ: `GET /api/merchant/pubkey` →
  `{key}` (base64 от PEM). Ключ кэшируется; при неверной подписи запрашивается заново
  (банк мог сменить ключ), но не чаще раза в 30 с.
- Ответ не 200 — monobank повторяет, до 3 раз. Порядок доставки не гарантирован.
- ⚠ Схема тела вебхука подписки в документации не описана. Поэтому телу мы не верим:
  подпись верна → состояние читается заново из `status` и `payments`. Заодно это снимает
  вопрос порядка и повторов. Повтор того же тела (SHA-256 уже записан) — 200 без действий.
- Ответы маршрута: 401 — подпись неверна; 404 — нет такого клиента; 503 — нет токена или
  не получен ключ; 502 — monobank не ответил на `status` (банк повторит вебхук).
- Страховка от потерянного вебхука: кабинет клиента сам спрашивает monobank при возврате
  с оплаты, пока подписка `pending`, и если состояние старше 6 часов.

## Включение

1. Саша: подключить интернет-эквайринг в `web.monobank.ua`, взять боевой токен; взять
   тестовый токен на `api.monobank.ua`.
2. Токены — в секреты GitHub (`MONO_TOKEN`, `MONO_TEST_TOKEN`) и в `/opt/ihor/shur-ads/env`.
   В репозиторий, чат и логи — никогда.
3. Actions → **Billing setup** (кладёт их в production Vercel), затем **Deploy** (ref=main).
4. Тестовый клиент (галочка «Тестовый клиент» в `/cabinet`) → «Оформити підписку» → оплата
   любой Luhn-картой → в кабинете «Підписка активна». Здесь же проверяется евро.
5. Только после этого — настоящий клиент. Пока `MONO_TOKEN` не задан, кнопки оплаты нет.

Выключить: `vercel env rm MONO_TOKEN production` и новый выкат. Действующие подписки при
этом продолжают списываться в monobank — их отменяют там же или до выключения.
